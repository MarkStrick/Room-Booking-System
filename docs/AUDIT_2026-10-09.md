# ผล Audit ความครบถ้วนของ KKU Space

ตรวจวันที่ 9 ตุลาคม 2569 เทียบ Request, DOCS, โค้ดปัจจุบัน และผลทดสอบในเครื่อง

ระบบมีกระบวนการจองหลักและ backend ที่ทดสอบผ่านแล้ว แต่ยังทำไม่ครบตาม Request และยังไม่พร้อมเปิดรับผู้ใช้จริง ช่องว่างสำคัญคือบริการภายนอก การบันทึกความผิดเมื่อยกเลิกช้า การตรวจความจุก่อนอนุมัติ วันหยุด อุปกรณ์รายชิ้น และงานบริหารข้อมูล/รายงาน

รายงานนี้แยก **ข้อกำหนดเดิม**, **บั๊กที่ทดลองยืนยัน**, **บริการที่ยังใช้ไม่ได้**, และ **ข้อเสนอที่ต้องตกลงนโยบาย** ไม่ตีความข้อเสนอทั้งหมดใน DOCS เป็นงานที่ได้รับอนุมัติแล้ว

## งานที่ควรแก้ก่อน

P1 หมายถึงควรปิดก่อน pilot ที่รับข้อมูลจริง ส่วน P2 คือความครบถ้วน/การใช้งาน/ข้อเสนอที่ต้องจัดลำดับต่อ ไม่มีการประเมินเป็นเปอร์เซ็นต์ เพราะเอกสารไม่มีน้ำหนักของ requirement และยังมีนโยบายขัดกัน

### F01 P1 บริการจริงยังไม่พร้อมและฐานข้อมูลต่อไม่ได้ในรอบนี้

**ประเภท:** สภาพแวดล้อมและการตรวจยืนยัน — UC2, UC11, UC13 และเส้นทางใช้งานจริงทั้งหมด

Google ไม่มี client configuration และ SMTP ไม่มีผู้ส่งที่พร้อมใช้งาน การสมัคร/ขอลิงก์รหัสผ่านจึงยังเปิดไม่ได้ตามเงื่อนไข `registrationReady()` ฐานข้อมูลจาก environment ในเครื่องเชื่อมไม่สำเร็จด้วย `ENOTFOUND` แม้ [SUPABASE_CONNECTION.md](../Room-Booking-System/docs/SUPABASE_CONNECTION.md) บันทึกว่าเคยเชื่อมผ่านแล้ว

**ทำต่อ:** ตรวจชื่อโฮสต์/DNS/สถานะ project และการเชื่อมต่ออีกครั้ง ตั้ง Google/SMTP/HTTPS ผู้ดูแลเริ่มต้นและข้อมูลห้องจริง จากนั้นทดสอบสมัคร → ยืนยันอีเมล/Google → จอง → อนุมัติ → รับอีเมล → เช็คอิน/จบรอบด้วยบัญชีจริง ยังไม่สรุปสาเหตุที่ละเอียดกว่าความล้มเหลว DNS จากหลักฐานนี้

**เกณฑ์ผ่าน:** connection diagnostics ผ่าน และมีผล E2E บน origin ที่จะเปิดใช้งานจริง รวม email delivery ไม่ใช่เพียงมี outbox หรือ SMTP รับคำสั่งแล้ว

### F02 P1 ยกเลิกช้าไม่บันทึกประวัติผิดเงื่อนไข

**ประเภท:** ข้อกำหนดเดิมยังไม่ครบ — ภาพรวมกระบวนการ, BR12 และ UC1/UC16

[domain.ts](../Room-Booking-System/packages/core/src/domain.ts) ช่วง `CANCEL` บรรทัด 333–354 ปฏิเสธด้วย `CANCELLATION_TOO_LATE` โดยไม่เพิ่ม `LATE_CANCEL`; [booking-service.ts](../Room-Booking-System/apps/backend/src/modules/booking-service.ts) ส่งข้อผิดพลาดออกจาก transaction จึงต้องออกแบบการบันทึกเหตุการณ์ให้ไม่ถูก rollback พร้อมการปฏิเสธด้วย

**ทดลองยืนยัน:** ยกเลิกรายการ APPROVED ก่อนเริ่ม 1 ชั่วโมง ได้ error ดังกล่าว และจำนวน violation คงเดิม 3 → 3 ทำให้ยอดความผิดที่ใช้พิจารณาบทลงโทษยังนับเฉพาะเหตุการณ์ที่มีการสร้างจริง เช่น no-show

**ทำต่อ:** ตกลงจังหวะการนับให้ตรงกันระหว่างปุ่มบนเว็บ/API และบันทึกครั้งเดียวต่อ booking/type โดยคงสถานะการจองเดิม การเปิดรายละเอียดหรือกด modal อย่างเดียวไม่ควรสร้างความผิด

**เกณฑ์ผ่าน:** ยืนยันยกเลิกช้าแล้วมี LATE_CANCEL หนึ่งรายการ ทำซ้ำไม่เพิ่มซ้ำ และคำขอที่ถูกปฏิเสธยังไม่กลายเป็น CANCELLED

### F03 P1 ลดความจุห้องแล้วอนุมัติคำขอที่เกินความจุได้

**ประเภท:** บั๊กที่ทดลองยืนยัน — ความถูกต้องของข้อมูล UC5/UC8/UC9

`BOOK` ตรวจจำนวนคนกับความจุ แต่ `ROOM_SAVE` ยอมลดความจุโดยไม่ตรวจรายการค้าง และ `DECIDE` ตรวจความว่างโดยไม่ตรวจความจุล่าสุด ดู [domain.ts](../Room-Booking-System/packages/core/src/domain.ts) บรรทัด 380–461

**ทดลองยืนยัน:** มี PENDING 4 คน → ผู้ดูแลแก้ความจุห้องเป็น 1 → อนุมัติสำเร็จเป็น APPROVED สำหรับ 4 คน

**ทำต่อ:** ป้องกันการลดความจุที่กระทบรายการที่ยังมีผล หรือแสดงผลกระทบและมีวิธีจัดการ พร้อมตรวจจำนวนคนซ้ำก่อนอนุมัติ

**เกณฑ์ผ่าน:** อนุมัติไม่ได้เมื่อจำนวนคนเกินความจุปัจจุบัน และการแก้ห้องที่มีรายการอนุมัติแล้วต้องมีพฤติกรรมชัดเจน

### F04 P1 กฎวันหยุดมีแล้วแต่ผู้ดูแลตั้งวันหยุดไม่ได้

**ประเภท:** ช่องว่างการใช้งานกฎเดิม — BR5 ส่วนวันหยุด

`availability()` ตรวจ `state.holidays` ได้ แต่ production เริ่มด้วย `holidays: []`; หน้า [Administration.tsx](../Room-Booking-System/apps/web/src/features/Administration.tsx) บรรทัด 239–251 แสดงรายการเท่านั้น และ [validation.ts](../Room-Booking-System/apps/backend/src/common/validation.ts) ไม่มีคำสั่งเพิ่ม/แก้/ลบวันหยุด คำแนะนำใน production setup ที่ให้ผู้ดูแลเพิ่มวันหยุดจึงยังทำผ่านแอปไม่ได้

**ทำต่อ:** เพิ่มการจัดการ/นำเข้าปฏิทินวันหยุดสำหรับผู้ดูแล พร้อมกำหนดวิธีจัดการ booking เดิมที่ได้รับผลกระทบ

**เกณฑ์ผ่าน:** ผู้ดูแลเพิ่มวันหยุดได้ ผู้ไม่มีสิทธิ์ทำไม่ได้ และการค้นหา/ส่งคำขอในวันนั้นถูกปฏิเสธจาก backend

### F05 P2 SLA 4 ชั่วโมงมีป้ายเตือนแต่ยังไม่มีงานติดตาม

**ประเภท:** ข้อกำหนดเดิมทำบางส่วนและข้อเสนอการติดตาม — BR7/UC8

[Bookings.tsx](../Room-Booking-System/apps/web/src/features/Bookings.tsx) บรรทัด 35–39 คำนวณจำนวนรายการเกิน 4 ชั่วโมงแล้ว แต่ [jobs.ts](../Room-Booking-System/apps/backend/src/modules/jobs.ts) ไม่มี reminder/escalation และไม่มีบันทึก approval deadline/SLA ที่ใช้รายงาน ไม่ใช่ฟังก์ชันที่ขาดทั้งหมด เพราะมีคำเตือนบนหน้าเจ้าหน้าที่แล้ว

**ทำต่อ:** ตกลงผู้รับแจ้งและจังหวะ reminder/escalation ให้เจ้าหน้าที่ทำทันกรอบเดิม ไม่มี requirement เดิมบังคับให้ auto-approve หรือ auto-reject หลัง 4 ชั่วโมง

**เกณฑ์ผ่าน:** รายการใกล้/เกิน deadline แจ้งผู้รับผิดชอบตามนโยบายและไม่สร้างแจ้งเตือนซ้ำ มีเวลาตัดสินที่ตรวจย้อนหลังได้

### F06 P2 จัดการห้องและอาคารยังไม่ครบการลบหรือเลิกใช้งาน

**ประเภท:** ข้อกำหนดเดิมยังไม่ครบ — UC9/UC10

มีเพิ่ม/แก้ห้อง อาคาร และจำนวนชั้น แต่ไม่มีคำสั่งลบ/soft delete/deactivate ห้องหรืออาคาร สถานะ CLOSED/MAINTENANCE ยังอยู่ในผลค้นหาเมื่อเลือกดูห้องไม่ว่าง ไม่ใช่ Inactive ที่ซ่อนจากการค้นหาตาม Scenario UC9 ชั้นเก็บเป็นตัวเลขและจำนวนชั้นของอาคาร ยังไม่มีข้อมูลชั้นแยกแบบ Floor ในแบบต้นทาง

**ทำต่อ:** รองรับเลิกใช้งานโดยรักษาประวัติ และป้องกันการลบข้อมูลที่มีความสัมพันธ์; กำหนดว่าต้องจัดการชั้นแยกหรือยืนยันการใช้จำนวนชั้นแบบปัจจุบัน

**เกณฑ์ผ่าน:** ห้องเลิกใช้งานไม่เสนอให้จองใหม่ ประวัติเดิมอ่านได้ และอาคาร/ชั้นที่มีห้องหรือ booking ผูกอยู่ไม่ถูกลบจนข้อมูลขาด

### F07 P2 รูปห้องและข้อมูลอุปกรณ์รายชิ้นยังไม่มี

**ประเภท:** ข้อกำหนดเดิมยังไม่ครบ — UC9/BR11/UC12

[contracts](../Room-Booking-System/packages/contracts/src/index.ts) ใช้ `scene` สำหรับภาพประกอบ และ `amenities: string[]` สำหรับสิ่งอำนวยความสะดวก ไม่มีรูปห้องจริง/image URL/upload และไม่มีจำนวน/สถานะของอุปกรณ์ประจำห้องแต่ละชนิด การตรวจห้องบันทึก condition/note ระดับห้องเท่านั้น ยังสรุปอุปกรณ์ชำรุดรายรายการไม่ได้

**ทำต่อ:** เพิ่มรูปห้องและข้อมูลอุปกรณ์ประจำห้องพร้อมจำนวน/สถานะ เชื่อมผลตรวจรายวันกับแต่ละรายการ และแสดงห้องที่ยังไม่ตรวจของวันนั้น ไม่สร้างผลตรวจแทนเจ้าหน้าที่อัตโนมัติ

**เกณฑ์ผ่าน:** เก็บรูปจริงได้ ตรวจว่าชิ้นใดชำรุด/จำนวนเท่าไรได้ และรายงานอุปกรณ์อ้างผลตรวจที่บันทึกจริง

### F08 P2 เพิ่มรายชื่อผู้เข้าร่วมยังปิดในโหมดเซิร์ฟเวอร์

**ประเภท:** ข้อกำหนดเดิมยังไม่ครบ — UC5 Scenario

[booking-service.ts](../Room-Booking-System/apps/backend/src/modules/booking-service.ts) บรรทัด 21 ปฏิเสธ BOOK ที่มี participants ทุกกรณี แม้ shared contract/domain รองรับ และ demo มีตัวเลือกดังกล่าว ระบุจำนวนคนได้แล้ว แต่ยังระบุผู้ร่วมใช้งาน/อีเมลไม่ได้

**ทำต่อ:** ตกลงการเลือกผู้ใช้ที่ลงทะเบียนกับการเชิญอีเมลภายนอก และตรวจสิทธิ์/ความเป็นส่วนตัวของ directory ก่อนเปิดใช้

**เกณฑ์ผ่าน:** เพิ่ม/ตรวจรายชื่อได้ใน server mode ตามนโยบาย และจำนวนรายชื่อสอดคล้องกับจำนวนคนโดยไม่เปิดข้อมูลผู้ใช้ให้ผู้ไม่เกี่ยวข้อง

### F09 P2 รายงานมีสถิติพื้นฐานและ CSV แต่ยังไม่ครบเนื้อหา

**ประเภท:** ข้อกำหนดเดิมทำบางส่วนและข้อเสนอ DOCS — UC12

[Reports.tsx](../Room-Booking-System/apps/web/src/features/Reports.tsx) มีจำนวนคำขอ เข้าใช้ no-show และชั่วโมงประมาณ พร้อม CSV รายการจอง ยังไม่มีรายงานสถานะ/ความเสียหายอุปกรณ์และอัตราการใช้ห้องเทียบเวลาที่เปิดบริการตามขอบเขตเดิม ส่วนรายงาน SLA, snapshot/export history เป็นรายละเอียดเพิ่มเติมใน architecture

ช่วงวันที่เริ่มต้นตรึงไว้ `2026-10-01` ถึง `2026-10-23` และสูตรชั่วโมงของ CHECKED_IN นับถึงเวลาจบรอบ แม้ขณะนั้นยังไม่จบ จึงควรอธิบายให้ชัดว่าคือประมาณการจนสิ้นรอบ หรือปรับหากต้องการรายงานชั่วโมงที่ผ่านไปแล้ว

**ทำต่อ:** ยืนยันสูตรและช่วงวันที่ปัจจุบัน เพิ่มรายงานที่อ้างข้อมูลอุปกรณ์/เวลาทำการจริง และทดสอบด้วย dataset ที่ทราบคำตอบ ไม่ถือว่า PDF/Excel เป็น requirement บังคับจากหลักฐานที่ตรวจ เพราะต้นทางกำหนดการส่งออกไฟล์โดยไม่ได้ล็อกชนิดไว้

**เกณฑ์ผ่าน:** ตัวเลขและไฟล์ส่งออกตรงชุดข้อมูลอ้างอิง โดยแจ้งนิยามสถานะและชั่วโมงที่นำมารวม

### F10 P2 เนื้อหาอีเมลยืนยันการยกเลิกยังไม่ครบ

**ประเภท:** ข้อกำหนดเดิมยังไม่ครบ — UC13

[domain.ts](../Room-Booking-System/packages/core/src/domain.ts) บรรทัด 353 สร้างเพียงข้อความรหัสรายการและยกเลิกแล้ว; worker ส่ง `notice.content` ตรง ๆ ใน [worker.ts](../Room-Booking-System/apps/backend/src/worker.ts) ขณะที่ Scenario ขอชื่อห้องและวันเวลาที่เคยจองด้วย ข้อมูลอีเมลกรณี no-show/ปิดห้องยังควรใช้รายละเอียดที่อ่านเข้าใจได้เช่นกัน

**เกณฑ์ผ่าน:** อีเมลระบุรหัส ห้อง วันเวลาเดิม เหตุผลตามเหตุการณ์ และส่งไปยังผู้จองถูกคน ตรวจเนื้อหาแยกจากการตั้ง SMTP

### F11 P2 ความช่วยเหลือมี FAQ และประวัติ แต่ทางออกเมื่อไม่พบคำตอบยังไม่ครบ

**ประเภท:** ข้อกำหนดเดิมทำบางส่วนและข้อเสนอ DOCS — UC7

มี tutorial, FAQ แบบ keyword และบันทึกประวัติสนทนาแล้ว แต่ FAQ เป็นค่าคงที่ใน [domain.ts](../Room-Booking-System/packages/core/src/domain.ts) ไม่ใช่ข้อมูลที่ผู้ดูแลแก้ผ่านแอปได้ คำตอบไม่พบเพียงแนะนำให้สอบถามเจ้าหน้าที่โดยไม่มีช่องทางติดต่อที่กดใช้ได้ตาม SSD และยังตอบสถานะ booking ของเจ้าของจากข้อมูลจริงไม่ได้

**ทำต่อ:** เพิ่มช่องทางติดต่อที่มีผู้รับผิดชอบ; ยืนยันว่าต้องการ FAQ ที่จัดการจากฐานข้อมูล/ถามสถานะส่วนตัวหรือเพียง FAQ กฎทั่วไป ไม่จำเป็นต้องเพิ่ม LLM เพื่อทำ FAQ ให้ครบ

## ข้อเสนอที่ต้องตกลงก่อนลงมือ

### D01 PENDING ถึงเวลาเริ่มหรือจบแล้วยังค้างอยู่

**ทดลองยืนยัน:** เลื่อนเวลาหลัง end ของ PENDING ไปหนึ่งวันแล้วเรียก `runTimers()` สถานะยังเป็น PENDING ทำให้ยังนับโควตารออนุมัติและกันยอดอุปกรณ์ หากเจ้าหน้าที่ไม่จัดการ ผู้ใช้ก็ยกเลิกเองตามกฎ 2 ชั่วโมงไม่ได้แล้ว

นี่เป็นช่องว่างนโยบายที่ architecture เสนอให้ยกเลิกโดยไม่คิดความผิด แต่ production setup ระบุว่ายังไม่เพิ่ม pending timeout จึงต้องตกลงสถานะ/เหตุผล/การแจ้งก่อนแก้ ไม่เท่ากับบังคับหมดอายุเมื่อครบ SLA 4 ชั่วโมง

### D02 ยอดกันอุปกรณ์ยังไม่ใช่การยืมคืนของจริง

ระบบคืนจำนวนอัตโนมัติเมื่อ COMPLETED/NO_SHOW/ยกเลิก/ปฏิเสธ และกันจำนวนรวมทุกวันตั้งแต่ PENDING ไม่มี ISSUED/RETURNED หรือ movement ตามข้อเสนอ [DATABASE_REVIEW.md](DATABASE_REVIEW.md) และ architecture

หาก pilot ครอบคลุมการส่งมอบอุปกรณ์จริง ต้องแยกจ่ายของ/คืนของ/ค้างคืนก่อนใช้ หากขอบเขตเป็นเพียง reservation ให้ประกาศข้อจำกัดและไม่ใช้ยอด remaining เป็นหลักฐานว่าของกลับมาแล้ว

### D03 ขอบเขตประวัติและข้อมูลส่วนบุคคล

ต้นทางกล่าวถึงแสดง 7 วัน/เก็บ 30 วัน แต่ Scenario ต้องดูประวัติทั้งหมดและรายงานระยะยาว หน้า StudentBookings ปัจจุบันแสดงทั้งหมด ไม่มี retention/archive job ข้อเสนอ DOCS เลื่อนการลบไว้จนมีนโยบาย

ต้องยืนยันช่วงแสดงผล ระยะเก็บ การ archive และช่วงนับความผิด ไม่ควรเพิ่มการลบเมื่อครบ 30 วันทันทีจนกระทบรายงานและหลักฐาน

### D04 เวลาทำการ minimum lead time และการมอบหมายตามช่วงวันที่

ยังไม่มีเวลาทำการต่ออาคาร ไม่มี minimum lead time 4 ชั่วโมง และ assignment ยังเป็น userId/roomIds ไม่มีวันเริ่ม-หมดอายุ ทั้งหมดเป็นข้อเสนอเสริมใน DOCS ไม่ใช่ข้อกำหนดเดิมที่ควรบังคับเพิ่มโดยไม่ตกลง

### D05 แนวทางขยายระบบและการปฏิบัติการ

Postgres adapter โหลดข้อมูลครบทุกตารางก่อนกรองสิทธิ์ และการเขียนทั้งหมดใช้ `app_lock` เดียว ส่วน rate limiter อยู่ใน memory ตาม [PRODUCTION_SETUP.md](../Room-Booking-System/docs/PRODUCTION_SETUP.md) จึงเหมาะกับ pilot ที่จำกัด instance ก่อน ยังไม่มีผล load test ตามปริมาณเป้าหมาย, restore drill, worker heartbeat monitoring หรือหลักฐาน Docker/CI ที่รันบนโฮสต์จริงในรอบนี้

OpenAPI และ API แยกตามทรัพยากรใน architecture ยังไม่ได้ทำ ปัจจุบันใช้ `/api/commands` กับ shared contracts การเปลี่ยน API รูปแบบนี้ควรเป็นการตัดสินใจออกแบบ ไม่ถือว่าฟังก์ชันจองหายไป

## DOCS และ Request ที่ต้องทำให้เป็นฉบับเดียวกัน

1. Architecture ยังระบุ Oracle และยังไม่มีโค้ด/ยังไม่ได้ scaffold ขณะที่ปัจจุบันเป็น React/NestJS/Supabase แล้ว ควรเพิ่มเอกสารสถาปัตยกรรมปัจจุบันหรือกำกับชัดว่าฉบับนี้เป็น historical proposal
2. PASSWORD_AUTH ระบุว่ายังไม่ส่ง migration ไป cloud แต่ SUPABASE_CONNECTION ระบุว่าติดตั้งแล้ว ไม่ควรใช้ข้อความใดข้อความหนึ่งยืนยันสถานะล่าสุดเมื่อ connection รอบนี้ล้มเหลว ควรบันทึกวัน/สภาพแวดล้อม/ผลตรวจล่าสุด
3. UC numbering ไม่ตรงกันระหว่างรายงาน เช่น UC5 เป็นทั้งจองและยกเลิก; SSD ยกเลิกบางภาพอ้างแจ้งเตือน UC15 ทั้งที่รายการหลักใช้ UC11/UC13 ควรทำ mapping ชื่อ/เลขเดียวก่อนแบ่งงานและตรวจส่งมอบ
4. BR10 จำกัดโดเมนขัดกับนโยบายใหม่เปิดทุกอีเมล และ Oracle schema ต่างจาก JSONB schema ปัจจุบัน เป็นการเปลี่ยนแบบที่ต้องบันทึก ไม่ใช่งานให้ย้อนกลับโดยอัตโนมัติ
5. IoT ถูกตัดจากขอบเขตหลักแล้ว แม้บางข้อความ/รายงานเก่ายังกล่าวถึง ไม่จัดการตัดไฟ/รายงานพลังงานเป็นงานค้างของรุ่นนี้
6. Request ยังขัดกันเรื่อง 7/30 วัน, นโยบายความผิด และแบบหลัง 4 ชั่วโมง ควรมี requirement decision log, ผู้ยืนยัน และ acceptance criteria ที่อ้างไฟล์/ข้อกำหนดได้
7. คู่มือ production ให้เพิ่มวันหยุดและเวลาทำการจากแอป แต่ปัจจุบันไม่มีหน้าหรือ API บันทึกข้อมูลเหล่านี้ครบ ควรแก้คู่มือให้ตรงจนกว่าจะพัฒนาเสร็จ
